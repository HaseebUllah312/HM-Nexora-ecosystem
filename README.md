# HM Nexora — Flutter App

A real, working Flutter conversion of the HM Nexora educational app UI, backed by a **free Firebase project** (Firestore + Firebase Auth) instead of local-only storage — so the same account and data can later be shared by a web app, a bot, and a browser extension, not just this mobile app.

## What's actually real vs. what's still mock

**Real, backed by Firebase (not just UI):**
- **Auth** — Register/Login/Logout/Forgot-password all call real Firebase Auth. Sessions persist across app restarts automatically.
- **Planner** — task checkboxes are saved per-account in Firestore.
- **AI Mentor** — chat history is saved per-account in Firestore (the replies themselves are still simulated — see below).
- **Community** — posts live in a shared Firestore collection. Likes, live counts, and posting a new message are all real and visible to every device signed in (once you've set up your own project).
- **Settings** — dark-mode switch and notification toggles persist per-account.
- **Profile** — shows the real signed-in user's name/email/student ID/department/year from Firestore.

**Still simulated / not wired to anything external:**
- **AI Mentor's replies** — canned text with a fake "typing" delay. Wire this to a real LLM (e.g. the Anthropic API) when you're ready; the chat plumbing (persistence, UI, history) is already there.
- **Google / Microsoft SSO buttons** on the login screen — show an honest "not connected yet" message rather than pretending to work.
- **Subjects, lectures, quizzes, assignments, study vault content, exam schedule** — realistic mock curriculum data, not per-user. Fine to leave static (it's reference content, not something users edit) or migrate to Firestore later if you want it centrally editable.
- **Dark mode** — the toggle saves your preference, but the app doesn't yet re-skin itself in a dark palette (every screen would need to read from a live `ThemeMode`, which is a bigger follow-up job).

## Why Firebase, and why it matters for your Web/Bot/Extension plans

You mentioned wanting this data usable from a future web app, a bot, and a browser extension. A purely local store (like `shared_preferences`) can't do that — it's locked to one device. Firebase's free Spark plan gives you:
- **Firestore** — one shared database, readable/writable from Flutter, JS (web + browser extensions), and Node.js (bots via the Admin SDK).
- **Firebase Auth** — the same login works across all of those, so a user signs in once and their data follows them everywhere.
- **No server to host or pay for** — it's a managed free service; the "database" is just a Firebase project, not something you run yourself.
- **Starts completely empty** — nothing is pre-loaded except the 3 sample community posts the app seeds itself the first time it runs against an empty database (see `seedCommunityIfEmpty()` in `firestore_service.dart`).

## Setup

### 1. Get the code into a real Flutter project

This zip contains only `lib/` and `pubspec.yaml` — no platform folders — since those need to be generated by the `flutter` CLI, which isn't available in the environment that produced this code.

```bash
flutter create hm_nexora
cd hm_nexora
rm -rf lib pubspec.yaml
cp -r /path/to/this/zip/lib .
cp /path/to/this/zip/pubspec.yaml .
```

### 2. Create your free Firebase project

1. Go to https://console.firebase.google.com → **Add project** → give it a name (e.g. "hm-nexora") → you can decline Google Analytics, it's not needed.
2. In the left sidebar: **Build → Authentication → Get started → Sign-in method → Email/Password → Enable**.
3. In the left sidebar: **Build → Firestore Database → Create database → Start in test mode** (fine for development; tighten the rules before shipping publicly — see below).

### 3. Connect the Flutter app to your project

From your project root:

```bash
dart pub global activate flutterfire_cli
flutterfire configure
```

Follow the prompts (pick your Firebase project, pick the platforms you want — Android/iOS/Web). This **overwrites `lib/firebase_options.dart`** with your real project's keys and drops in the native config files (`google-services.json`, etc.) automatically. The placeholder version currently in this zip will not connect to anything — you must run this step.

### 4. Install dependencies and run

```bash
flutter pub get
flutter run            # picks a connected device/emulator
flutter run -d chrome  # or run in a browser
```

Register a new account on first launch — that's what creates your first real user in Firebase Auth + Firestore.

### 5. (Before showing this to real users) lock down Firestore rules

Test mode allows anyone to read/write anything — fine for development, not for production. In the Firebase console → Firestore → Rules, tighten it to something like:

```
rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
      match /private/{doc} {
        allow read, write: if request.auth != null && request.auth.uid == uid;
      }
    }
    match /community_posts/{postId} {
      allow read: if request.auth != null;
      allow create: if request.auth != null;
      allow update: if request.auth != null; // needed for like-toggling
    }
  }
}
```

## Testing & CI

- `flutter test` runs the included unit + widget tests locally.
- Pushing this to GitHub triggers `.github/workflows/flutter_ci.yml`, which runs `flutter analyze` and `flutter test` on a real GitHub-hosted runner — that's the actual compile/type-check this code has been through, since the environment that wrote it had no Flutter SDK access. Treat a green CI run as the real correctness signal, more than anything in this README.
- The workflow's two build-verification steps (Android/Web) are marked best-effort (`continue-on-error`) because they need the platform folders and `google-services.json` that only exist after you run `flutterfire configure` locally and commit them — `analyze` + `test` are what actually catch broken Dart code.

## Error handling

Every Firestore read on screen load (Settings, Planner, AI Mentor) is wrapped in try/catch/finally — a network failure falls back to sensible defaults instead of hanging on a loading spinner forever. Every "fire and forget" write (task toggles, likes, chat history, settings) catches its own errors so a dropped connection doesn't throw unhandled exceptions; a few surface a SnackBar so the user knows a save didn't go through.

## A note on how this was built

This app was hand-written in a sandboxed environment without the Flutter SDK, Dart, or network access to pub.dev/firebase-tooling domains — confirmed by trying: cloning the Flutter SDK via GitHub succeeded, but its Dart SDK download (hosted on `storage.googleapis.com`) was blocked outright. So nothing here was compiled before delivery. What *was* done: every service method's signature was cross-checked by hand against every call site across all screens, brace/paren/import balance was verified file-by-file, a duplicated bit of logic (name-to-initials, previously copy-pasted three different ways) was consolidated into one tested function, and real unit + widget tests plus a CI workflow were added so the first real build happens automatically and verifiably on GitHub rather than silently on your machine.

**You'll still be the first to run `flutter pub get`.** If it or `flutter run` throws errors, paste them back — first-build issues on hand-written Flutter/Firebase code are normal and usually small (a missing import, a version mismatch), not structural problems.
